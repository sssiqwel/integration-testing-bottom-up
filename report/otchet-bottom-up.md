# Отчёт по лабораторной работе

## Интеграционное тестирование методом «снизу вверх»

## Цель работы

Освоить метод интеграционного тестирования «снизу вверх» на примере учебного проекта: начать с базовых модулей (хранилищ и моделей), постепенно подключать модули более высокого уровня, на каждом этапе фиксировать результаты и найденные проблемы.

## Задание

1. Выбрать проект.
2. Применить метод «снизу вверх»: начать с базовых модулей — хранилищ и сервисов.
3. Постепенно интегрировать модули более высокого уровня: HTTP-клиент, контроллеры.
4. Выполнить интеграционные тесты на каждом этапе, записать результаты и проблемы.
5. Подготовить отчёт с ходом тестирования, найденными проблемами и выводами об эффективности метода.

## 1. Теоретическая часть

Метод «снизу вверх» (bottom-up) — это инкрементальный способ интеграционного тестирования, обратный методу «сверху вниз». Сначала тестируются самые нижние модули, которые ни от кого не зависят. Модулей, которые должны их вызывать, ещё нет, поэтому вместо них пишутся драйверы (driver). Драйвер — это тестовый код, который вызывает модуль так, как его вызывал бы модуль уровнем выше. Когда нижний уровень проверен, к нему подключается следующий, и так до самого верхнего модуля.

Плюсы метода:

- заглушки не нужны: каждый модуль работает с уже проверенными настоящими модулями под ним;
- дефекты в нижних модулях (хранение данных, клиенты) находятся рано;
- при ошибке на новом уровне понятно, что нижние уровни уже проверены, значит проблема в новом модуле или в связи с ним.

Минусы метода:

- нужно писать драйверы;
- верхний модуль (то, что видит пользователь) проверяется в самом конце, поэтому ошибки в главной логике находятся поздно;
- пока не собран верхний уровень, нельзя показать работающий сценарий целиком.

## 2. Описание проекта

Я использовал тот же учебный проект `user-order-services`, что и в работе «сверху вниз», чтобы сравнить два метода на одном коде. В нём два сервиса на FastAPI, данные хранятся в памяти.

**Users API:** `models.py` (модели и проверка имени и email), `storage.py` (хранилище, при запуске есть Анна id=1 и Пётр id=2), `auth.py` (Bearer-токен), `main.py` (эндпоинты).

**Orders API:** `models.py` (заказ и снимок пользователя), `storage.py` (хранилище заказов), `auth.py`, `users_client.py` (HTTP-клиент к Users API), `main.py` (эндпоинты).

### 2.1. Уровни модулей

Для метода «снизу вверх» модули нужно разложить по уровням так, чтобы каждый уровень зависел только от уровней ниже.

```
Уровень 4   Orders API: main.py (контроллер)         ← подключаю последним
               │
Уровень 3   Orders: users_client.py ──HTTP──┐
                                            ▼
Уровень 2                         Users API: main.py + auth.py
                                            │
Уровень 1   Orders: models + storage     Users: models + storage   ← начинаю отсюда
```

### 2.2. Порядок подключения и драйверы

| Этап | Уровень | Что тестируется | Драйвер (кто вызывает вместо верхнего модуля) |
|---|---|---|---|
| 1 | 1 | Users: models + storage | тест вызывает `UserStorage` напрямую |
| 2 | 1 | Orders: models + storage | тест вызывает `OrderStorage` напрямую |
| 3 | 2 | Users API (контроллер + auth над этапом 1) | HTTP-клиент в тесте вместо Orders API |
| 4 | 3 | users_client + настоящий Users API | тест вызывает `get_user()` вместо контроллера Orders |
| 5 | 4 | контроллер Orders API над всем, что ниже | HTTP-клиент в тесте вместо пользователя, это уже полная система |

Заглушек в этой работе нет. Единственное исключение — на этапе 4 и 5 я один раз подменил адрес Users API на несуществующий, чтобы проверить ситуацию «Users API выключен».

## 3. Ход работы

### 3.1. Как устроены тесты

Тесты лежат в папке `tests`, по одному файлу на этап. На этапах 1 и 2 драйвер — это просто вызовы методов Python. Начиная с этапа 3 сервисы запускаются через uvicorn в отдельных потоках, и тесты ходят к ним по настоящему HTTP. Перед каждым тестом хранилища очищаются.

Перезапуск Users API я имитирую сбросом его хранилища (`storage.reset()`): данные хранятся в памяти, поэтому при настоящем рестарте происходит то же самое.

Тесты с найденными дефектами помечены `xfail(strict=True)`, как и в прошлых работах.

Запуск по этапам:

```bash
make test
```

Скрипт `run_stages.sh` запускает этапы строго по порядку снизу вверх и сохраняет вывод каждого в `results/`. Если нижний этап упал, верхние не запускаются: нельзя подключать модуль поверх неработающего.

## 4. Найденные дефекты

### BU-D1. При неверной схеме авторизации сообщение «нет заголовка»

**Серьёзность:** низкая. **Где найден:** этап 3. **Модуль:** `auth.py` (одинаковый в обоих сервисах).

**Шаги:** `POST /api/v1/users` с заголовком `Authorization: Basic c2VjcmV0`.

**Ожидаемый результат:** 401 с понятным текстом про неподдерживаемую схему.

**Фактический результат:** 401 `Missing Authorization header`, хотя заголовок передан.

Так как `auth.py` в Orders API такой же, дефект есть и там.

### BU-D2. Один пропавший пользователь роняет весь список заказов

**Серьёзность:** высокая. **Где найден:** этап 5. **Модуль:** `orders_service/app/main.py`, `list_orders` + `enrich_order`.

**Шаги:**

1. Создать заказ для Анны (id=1).
2. Создать пользователя (id=3) и заказ для него.
3. Перезапустить Users API — пользователь 3 пропадает.
4. `GET /api/v1/orders`.

**Ожидаемый результат:** 200 и список, где есть хотя бы заказ Анны.

**Фактический результат:** `404 {"detail": "User 3 not found"}`.

### BU-D3. Существующий заказ после рестарта Users API отвечает 404

**Серьёзность:** высокая. **Где найден:** этап 5. **Модуль:** `main.py`, `get_order` + `enrich_order`.

**Шаги:** создать пользователя и заказ, перезапустить Users API, `GET /api/v1/orders/1`.

**Ожидаемый результат:** ответ, по которому видно, что заказ есть, а пользователь недоступен.

**Фактический результат:** `404 {"detail": "User 3 not found"}` — по коду не отличить от «заказа нет».

### BU-D4. После рестарта Users API заказ показывает другого человека

**Серьёзность:** критическая. **Где найден:** этап 5, риск замечен на этапе 1. **Модули:** `users_service/app/storage.py` + связь с Orders API.

**Шаги:**

1. Создать пользователя Иван (id=3) и заказ «Подарок Ивану».
2. Перезапустить Users API.
3. Создать пользователя Мария — она получает тот же id=3.
4. `GET /api/v1/orders/1`.

**Ожидаемый результат:** заказ Ивана не показывает чужие данные.

**Фактический результат:**

```
{"id":1,"user_id":3,"item":"Подарок Ивану","quantity":1,
 "user":{"id":3,"name":"Мария Сидорова","email":"maria@example.com"}}
```

Это утечка персональных данных. Причина — то, что я увидел ещё на этапе 1: после рестарта счётчик id в Users API начинается заново, а Orders API хранит только `user_id`.

### Наблюдения

- **N+1 запросов.** Для списка из 10 заказов одного пользователя Orders API 10 раз запросил одного и того же пользователя. Это видно по счётчику вызовов в тесте bu5_04, время в заголовке — около 7–8 мс.
- **`/health` не видит зависимость.** При выключенном Users API заказы отвечают 503, а `/health` — 200.

## 5. Анализ эффективности метода

### 5.1. На каком этапе что нашлось

| Проблема | Где замечена | Где подтверждена |
|---|---|---|
| id начинаются заново после рестарта | этап 1 (наблюдение) | этап 5 (BU-D4) |
| строгий UserSnapshot | этап 2 (наблюдение) | этап 4 — не подтвердилась |
| BU-D1, схема Basic | этап 3 | — |
| BU-D2, список падает целиком | этап 5 | — |
| BU-D3, 404 на существующий заказ | этап 5 | — |

На нижних уровнях (этапы 1–4) почти всё прошло. Это ожидаемо: хранилища, модели, Users API и HTTP-клиент написаны аккуратно. Три из четырёх дефектов нашлись только на последнем этапе, когда подключился контроллер Orders API, потому что главная ошибочная логика находится именно в нём.

### 5.2. Сравнение с методом «сверху вниз»

Я тестировал один и тот же проект обоими методами, поэтому их можно сравнить напрямую.

| Дефект | «Сверху вниз» | «Снизу вверх» |
|---|---|---|
| Список падает целиком | этап 1 из 5 (TD-D1) | этап 5 из 5 (BU-D2) |
| 404 на существующий заказ | этап 1 (TD-D2) | этап 5 (BU-D3) |
| Ответ Users API не по контракту → 500 | этап 1 (TD-D3) | **не найден**, только наблюдение |
| Схема Basic | этап 2 (TD-D4) | этап 3 (BU-D1) |
| Повторные id, чужие данные в заказе | этап 5 из 5 (TD-D5) | этап 1 — риск, этап 5 — подтверждён (BU-D4) |
| Тестов / прошло / дефектов | 36 / 28 / 8 | 45 / 41 / 4 |

Что я заметил:

- **Дефекты контроллера «снизу вверх» находит поздно.** TD-D1 и TD-D2 «сверху вниз» нашёл на первом этапе, а здесь они появились только на последнем.
- **Зато риск в нижнем модуле виден рано.** Проблему с повторными id я заметил уже на этапе 1, когда тестировал хранилище Users API отдельно. В методе «сверху вниз» хранилище Users API подключается последним, и я узнал о проблеме только в конце.
- **Без заглушек не проверить то, чего настоящий модуль не делает.** Дефект с лишним полем (TD-D3) «снизу вверх» не нашёл. Настоящий Users API сейчас отдаёт ровно три поля, контракт совпадает, и тест на этапе 4 честно проходит. В «сверху вниз» заглушка вернула лишнее поле, и сразу стало видно, что Orders API падает с 500.
- **Тестов больше, но они проще.** Драйверы — это обычные вызовы функций и HTTP-запросы, писать их проще, чем заглушки. И я не мог ошибиться в поведении заглушки, потому что все модули настоящие.

### 5.3. Удобно ли было локализовать ошибки

Да. Когда на этапе 5 упали три теста, я уже знал, что хранилища, Users API и HTTP-клиент проверены на этапах 1–4 и работают правильно. Значит, искать ошибку нужно было только в контроллере Orders API. По сравнению с «большим взрывом» это намного удобнее: там те же самые ответы `404 User 3 not found` могли быть вызваны любым из модулей.

## Вывод

В ходе работы я применил метод «снизу вверх» к проекту Users API + Orders API. Начал с моделей и хранилищ обоих сервисов, затем подключил Users API, HTTP-клиент Orders API и в конце контроллер Orders API. На каждом этапе тесты запускались отдельно, и результаты сохранены в `results/`.

Всего 45 тестов: 41 прошёл, 4 воспроизводят найденные дефекты. Найдено 4 дефекта (один критический, два высокой серьёзности, один низкой) и 2 наблюдения.

Метод «снизу вверх» хорошо проверил нижние модули и рано показал риск с повторными id, который потом оказался самым опасным дефектом. Ошибки было легко локализовать, потому что всё ниже нового модуля уже было проверено. Но для этого проекта метод оказался менее эффективным, чем «сверху вниз»: основная логика и большинство дефектов находятся в верхнем модуле, поэтому они нашлись только на последнем этапе, а дефект с нарушением контракта без заглушек не нашёлся вообще.

Я думаю, что лучше всего совмещать оба метода: «снизу вверх» для хранилищ и клиентов, «сверху вниз» для контроллеров и обработки ошибок от зависимостей.

