# Интеграционное тестирование методом «снизу вверх»

Лабораторная по курсу «Интеграционное тестирование». По заданию нужно было протестировать проект методом «снизу вверх»: начать с базовых модулей вроде хранилищ и сервисов, потом постепенно подключать модули уровнем выше, вплоть до контроллеров, и на каждом этапе записывать, что прошло и что сломалось.

Полный отчёт — в [`report/otchet-bottom-up.md`](report/otchet-bottom-up.md), вариант для Word — `report/Otchet-bottom-up.docx`. Ниже коротко, что я сделал и как это запустить.

## Какой проект я тестировал

Взял наш учебный проект из двух сервисов на FastAPI:

- **Users API** — пользователи (при запуске уже есть Анна, id=1, и Пётр, id=2);
- **Orders API** — заказы. При создании и при чтении заказа он обращается в Users API за данными пользователя.

Всё хранится в памяти. Код сервисов лежит в `users_service/` и `orders_service/`, я скопировал его сюда без изменений, чтобы репозиторий запускался отдельно.

## Как я применял метод

Сначала разложил модули по уровням: снизу то, что ни от кого не зависит, сверху то, что вызывает всех остальных.

```
уровень 4   контроллер Orders API
уровень 3   HTTP-клиент Orders → Users API
уровень 2   Users API (контроллер + проверка токена)
уровень 1   модели и хранилища обоих сервисов
```

Заглушек в этой работе нет вообще, все модули настоящие. Зато нужны драйверы — это код, который вызывает модуль вместо ещё не подключённого модуля сверху. У меня драйверами работают сами тесты: на нижних уровнях они просто вызывают методы хранилища, а выше шлют HTTP-запросы.

Этапов пять, каждый в своём файле в `tests/`:

1. `test_bu1_users_storage.py` — модели и хранилище пользователей.
2. `test_bu2_orders_storage.py` — модели и хранилище заказов.
3. `test_bu3_users_api.py` — Users API целиком, поверх проверенного хранилища.
4. `test_bu4_users_client.py` — HTTP-клиент Orders API вместе с настоящим Users API. Тест сам вызывает `get_user()`, потому что контроллера Orders ещё нет.
5. `test_bu5_orders_api.py` — подключаю контроллер Orders API, и это уже вся система.

## Что нашлось на каждом этапе

**Этап 1** прошёл полностью, но я заметил одну вещь: после сброса хранилища номера пользователей снова начинаются с 3. Для одного хранилища это нормально, но Orders API хранит у себя `user_id`, поэтому я записал это как риск и решил проверить в конце.

**Этап 2** тоже прошёл. Отметил, что снимок пользователя в заказе (`UserSnapshot`) не принимает лишних полей — непонятно было, плохо это или нет.

**Этап 3** — первый дефект, **BU-D1**: при заголовке `Authorization: Basic ...` сервис пишет «Missing Authorization header», хотя заголовок передан. Файл `auth.py` одинаковый в обоих сервисах, так что и в Orders то же самое.

**Этап 4** прошёл. Тут же закрыл вопрос со второго этапа: Users API отдаёт ровно те поля, что ждёт `UserSnapshot`, так что сейчас ничего не ломается.

**Этап 5** — сразу три дефекта:

- **BU-D2.** После перезапуска Users API один пропавший пользователь роняет весь список заказов: `GET /api/v1/orders` отвечает 404.
- **BU-D3.** Существующий заказ после перезапуска Users API отвечает 404, будто заказа нет.
- **BU-D4.** Тот самый риск с первого этапа подтвердился, и это самый серьёзный дефект: после перезапуска новый пользователь получает старый номер, и в чужом заказе показываются его имя и email.

Плюс два наблюдения: на список из 10 заказов одного пользователя сервис 10 раз ходит в Users API, а `/health` отвечает 200, даже когда Users API выключен.

Тесты на дефекты помечены `xfail(strict=True)`: общий прогон остаётся зелёным, а `make defects` показывает их как обычные падения.

Мой вывод: нижние модули метод проверил хорошо, а риск с номерами пользователей я увидел уже на первом этапе. И когда на пятом этапе всё упало, было ясно, что ошибка в контроллере Orders: всё, что под ним, уже проверено. Но для этого проекта метод не самый удобный — основная логика как раз в контроллере, поэтому большая часть дефектов вылезла только на последнем этапе.

## Как запустить у себя

Понадобится Python 3.12+ и `make`.

```bash
git clone <ссылка на этот репозиторий>
cd integration-testing-bottom-up
make install
make test
```

`make install` создаёт `.venv` и ставит зависимости. Сервисы вручную запускать не надо, тесты поднимают их сами.

`make test` запускает этапы строго снизу вверх. Если нижний этап упадёт, верхние не запустятся: строить модуль поверх неработающего бессмысленно. Вывод каждого этапа пишется в `results/`.

В конце у меня выходит:

```
test_bu1_users_storage: ok — 10 passed
test_bu2_orders_storage: ok — 11 passed
test_bu3_users_api: ok — 8 passed, 1 xfailed
test_bu4_users_client: ok — 6 passed
test_bu5_orders_api: ok — 6 passed, 3 xfailed
```

Найденные дефекты как обычные падения:

```bash
make defects
```

Должно получиться `4 failed` — по одному тесту на каждый дефект.

Один этап отдельно:

```bash
.venv/bin/python -m pytest tests/test_bu1_users_storage.py -v
```

## Что где лежит

```
users_service/     Users API
orders_service/    Orders API
tests/
  lab_kit.py       загрузка обоих сервисов в один процесс и запуск на uvicorn
  conftest.py      фикстуры: сервисы, очистка данных перед каждым тестом
  test_bu1..5_*.py этапы
results/           вывод тестов по этапам
report/            отчёт (.md и .docx)
run_stages.sh      запуск этапов по очереди
```

Небольшая техническая деталь: оба сервиса называют свой пакет `app`, и в один процесс их просто так не загрузить. Для этого в `lab_kit.py` написана функция `load_service`. А перезапуск Users API я имитирую сбросом его хранилища — данные всё равно в памяти, так что при настоящем рестарте происходит ровно то же самое.
